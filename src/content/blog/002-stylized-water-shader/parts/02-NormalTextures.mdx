## Chapter II: Normal textures

With displacement I had motion, but not the richness I wanted. The waves moved, but they didn't feel detailed or varied.  
To push further, I turned to one of the most common tricks in real-time rendering: ==normal maps==.

By now the word _normal_ should feel familiar. The _map_ part simply means a texture — one of the GPU's most
fundamental data structures. A texture isn't just an image, it's an array of values (plus metadata like format,
dimensions, mipmaps, filtering) that the GPU can interpret however we decide. Sometimes that means colors
(diffuse/albedo), other times directions (normals), heights (displacement), or occlusion. At shader level, all you
really see is a grid of texels waiting to be read.

This second attempt flipped the logic of my first. Instead of forcing the geometry to ripple, I let the fragments
fake the ripples directly. I kept the same flat plane, nudged slightly at the shoreline so it wouldn't look cut out,
and layered scrolling normal maps on top. The geometry hardly moved, but the surface finally had texture and motion.

The difference was immediate. Light scattered and shifted with the ripples. For the first time, the lake had a surface
I could believe in.

### A short detour: Textures, color spaces, and normal maps

Before going deeper, it's worth pausing on how normal maps are stored and interpreted. A lot can silently go wrong here.

This is what the normal map I used looks like. To make sense of it, let's peel back a few layers.

<br />

**Pixels as vectors**

At its core, a pixel is just a `vec4(r, g, b, a)`. In a photo those values mean colors. In a normal map they represent
a direction: `vec3(x, y, z)`. Alpha is often unused.

Since most normals point "up" (Z &#8776; 1), the blue channel is bright, while red and green (X and Y) wiggle slightly
for sideways slopes. That's why normal maps usually look purple, you're really looking at coordinates disguised as color.

<br />

**Color spaces**

Most everyday textures are in ==sRGB==, which has a gamma curve baked in so they look right to our eyes. That's fine
for photos, but terrible for data.

Normal maps must stay ==linear==. If you accidentally sample them as sRGB, the gamma curve distorts the vectors.
The math still runs, but highlights look muddy and reflections drift. It's one of those subtle bugs that can waste hours.

<br />

**Tangent space**

Most normal maps are baked in _tangent space_:

- Red &rarr; tangent (left/right)
- Green &rarr; bitangent (up/down)
- Blue &rarr; normal (outward)

Lighting, however, happens in _world_ or _view space_. So the tangent-space vector has to be transformed by the TBN
(tangent, bitangent, normal) basis.

On my static flat plane I could hard-code this basis. For an arbitrary mesh you'd want tangents/bitangents from geometry
(or derivatives), so the normals rotate properly with the surface.

But lighting happens in world or view space, so we need to transform.

```typescript
class WaterMaterial extends MeshBasicNodeMaterial {
  // ...
  private sampleTangentNormal = Fn(([uvCoords = vec2(0)]) => {
    const tex = texture(assetManager.waterNormal, uvCoords); // [0..1]
    const tangentN = tex.rgb.mul(2).sub(1); // unpack to [-1..1]
    return tangentN;
  });

  private tangentToObject = Fn(([tangentN = vec3(0)]) => {
    // hard-coded TBN basis for a flat plane (U → +X, V → −Z, N → +Y)
    const T = vec3(1, 0, 0); // Tangent
    const B = vec3(0, 0, -1); // Bitangent
    const N = vec3(0, 1, 0); // Normal
    return tangentN.x.mul(T).add(tangentN.y.mul(B)).add(tangentN.z.mul(N));
  });

  private objectToWorld = Fn(([objectN = vec3(0)]) => {
    return normalize(modelNormalMatrix.mul(objectN));
  });
  // ...
}
```

> Some normal maps follow DirectX's convention with the green channel flipped. If your highlights look inverted,
> try negating Y, or equivalently the bitangent.

### Layering the motion

One scrolling normal map looks fake quickly. The repetition jumps out. The trick is layering.

I sampled the same texture three times, at different scales and speeds, each scrolling in a slightly different
direction. By using odd ratios (2.7, 3.1, not neat integers), the patterns never lined up perfectly, so the motion
kept drifting and never tiled in sync.

Each layer contributed a different "frequency": broad slow undulations, mid-scale ripples, and fast surface noise.
After blending I normalized the result back to unit length, **crucial**, otherwise the vectors drift in magnitude and
the lighting breaks.

Conceptually it was just three scrolling textures. But visually, it gave the surface motion at every scale, from
gentle swells to tiny ripples.

<br />

### Outcome

This version wasn't about performance, it was about results.

Instead of pushing thousands of vertices like before, I let the GPU fake detail with normal maps. The cost shifted
from vertex count to fragments, a few extra texture fetches per pixel. GPUs are very good at that, especially when
sampling the same image, so it was a fair trade. Resolution and overdraw mattered far more than vertex density now.

More importantly, this stage forced me to really understand normals: how they're stored, sampled, transformed,
and how fragile they can be if you get color space wrong. Those lessons carried into every shader I wrote afterwards.

It wasn't lush or stylized yet, but it was the first time the water in Revo truly felt like water.
