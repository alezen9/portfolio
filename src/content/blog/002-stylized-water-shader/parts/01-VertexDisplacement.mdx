## Chapter I: Vertex displacement

My first attempt began with the most straightforward idea: if you want waves, move the surface up and down.

That's the essence of _vertex displacement_. Each vertex is fed into a function of sine waves, noise, or both,
time is added to the input, and the mesh begins to ripple.

Intuitively, more vertices in the geometry mean more detail: there's less guesswork between points,
and the motion appears smoother.

This technique works, but it isn't enough to sell the effect. Even with vertices shifting around, the surface
can still look flat.

That's because I started from a flat plane. The pipeline had no idea I was moving vertices around, so by default it treated
every face as if nothing had changed

To fix that, I had to give the renderer a hint about how each displaced face was really tilted. That's where
==normals== come in.

<br />

### What is a normal?

A normal is a 3D unit vector that tells the renderer which way a surface is facing.

They're essential for lighting and reflections because they define the angle at which light hits a ==fragment==.  
Without them, the renderer would have no basis for shading, every surface would look flat, unaffected by light.

Normals are stored **per vertex** and then interpolated across each triangle, so every fragment gets
an approximate orientation.

When a shape has a sharp edge, normals can't be shared across it. The vertex at that corner has to be
duplicated so each copy can carry its own normal.

Take a cube: it has 8 corners, but in practice we use 24 vertices: 4 for each face.  
If we only used 8, the normals would be averaged across the joins, and the cube would look oddly rounded.

Normals define how light hits the surface, but they only make sense in context: which part of the screen are we shading?
That's where ==fragments== enter the picture.

<br />

### What is a fragment?

Fragments and normals go hand in hand.

Internally, all meshes are broken down into tiny triangles (primitives).  
When one of those triangles overlaps a pixel on screen, the rasterizer produces a **fragment**:
a candidate contribution to that pixel's final color.

If several triangles overlap the same pixel, multiple fragments are generated in the same frame.
Each fragment runs through the **fragment shader** (called a _pixel shader_ in DirectX), which decides its color.
It then passes through a series of per-fragment tests (depth, stencil, alpha). Some are kept and blended, others
discarded.

In this case, the same pixel is covered first by the sky, then the ground, then a box, and finally a sphere.  
Each overlap generates a fragment, but only the front-most opaque one wins. If blending is enabled (transparency, additive, etc.),
several may be combined instead of being thrown away.

> Shading fragments that never affect the final image is called **overdraw**. GPUs reduce it with early depth tests or
> front-to-back rendering, but with transparency or other blending modes, even hidden fragments may still contribute.

### Shading waves

With normals and fragments understood, I could finally shade the displaced surface in a way that light reacted properly.

Back to my water: at this point the mesh was rippling up and down, but it still looked flat.

On a plain mesh all vertex normals point upward, so the light bounces in a uniform, lifeless way. I wanted the
normals to follow the displaced surface, so that each fragment would react differently to the light.

The way to achieve that was to recompute normals dynamically. A common trick is the ==neighbor technique==:

1. Compute the elevation for two nearby points, slightly offset on X and Z by a small `ε`.
2. Compute the elevation for the current vertex.
3. Build two direction vectors from the current position to those neighbors.
4. Take their cross product and normalize, that gives a new normal pointing outward from the displaced surface.

<br />

> The **cross product** is the key step: it takes two surface-aligned vectors and produces a third that sticks out
> perpendicular to both. Since the neighbors lie on the displaced surface, the result naturally points the right
> way for shading.

<br />

```typescript
class WaterMaterial extends MeshBasicNodeMaterial {
  // ...
  private computeElevation = Fn(([posXZ = vec2(0)]) => {
    /* ... */
  });

  private computeNormal = Fn(() => {
    const epsilon = float(0.01); // tune to your scale (world units)

    // X neighbor
    const xNeighborPosition = positionLocal.add(vec3(epsilon, 0, 0));
    const xNeighborElevation = this.computeElevation(xNeighborPosition.xz);
    const xNeighborPositionElevated = xNeighborPosition.add(
      vec3(0, xNeighborElevation, 0),
    );

    // Z neighbor
    const zNeighborPosition = positionLocal.add(vec3(0, 0, epsilon));
    const zNeighborElevation = this.computeElevation(zNeighborPosition.xz);
    const zNeighborPositionElevated = zNeighborPosition.add(
      vec3(0, zNeighborElevation, 0),
    );

    // current vertex
    const elevation = this.computeElevation(positionLocal.xz);
    const currentPositionElevated = positionLocal.add(vec3(0, elevation, 0));

    // order matters (right-hand rule), pick one and stay consistent
    const toXNeighbor = normalize(
      xNeighborPositionElevated.sub(currentPositionElevated),
    );
    const toZNeighbor = normalize(
      zNeighborPositionElevated.sub(currentPositionElevated),
    );
    const computedNormal = normalize(cross(toXNeighbor, toZNeighbor));

    return computedNormal;
  });
  // ...
}
```

> Picking the right value for `ε` was a balancing act. Too large and I'd smear away fine detail, too small
> and floating-point noise would creep in. And since each neighbor adds another texture fetch, the cost scaled
> quickly with vertex count.

<br />

With dynamic normals in place, the ripples finally caught light. They weren't perfect, but they gave life to what
had been just a wobbly mesh.

<br />

### Outcome

While experimenting, I came across a great [YouTube demo by Dan Greenheck](https://www.youtube.com/watch?v=jK4uXGY07vA).
He built a `WebGL` version with this same neighbor trick, and his result looked fantastic.

My take was lighter. I skipped some steps, leaned on a precomputed noise texture instead of generating noise
procedurally, and simplified the math. That texture itself was a neat shortcut: I packed three tiled patterns
(Perlin, Voronoi, Turbulence) into its RGB channels and blended between them. It gave motion, though with less
richness than Dan's multi-octave approach.

Each vertex sampled the texture a few times: once for itself and twice for its neighbors. With only a few thousand
vertices and the same texture reused, it wasn't a deal-breaker. Still, it reminded me that cost scales differently
depending on where the work happens: vertex fetches scale with vertex count, fragment fetches with resolution and
screen coverage.

The bigger limitation, though, wasn't sampling. It was geometry. Displacement can only move vertices that exist,
so if the mesh is coarse, ripples will always look blocky. To get better detail without pushing absurd vertex counts,
I built a custom lake mesh in Blender: extra subdivisions where the water was visible, none under the terrain where
they'd be wasted.

If you're curious, the full shader is [here](https://github.com/alezen9/revo-realms/blob/5966b11b4d442aa0c08025f03a34e589a510ffcf/src/entities/Water.ts),
written in TSL (Three Shading Language).

In my implementation, I used a slight variation: instead of elevating three points and crossing them, I approximated
slopes, built tangent and bitangent vectors, and crossed those. Mathematically it's equivalent, and at the time it
felt cleaner since I only had to deal with elevations. Looking back, though, the three-points method is easier to
picture, and if I were starting fresh today, I'd probably choose that.

To finish, I added a hint of environment reflection and a Fresnel effect. Nothing dramatic, but enough to push
the surface a bit closer to water instead of just "bumpy mesh".
