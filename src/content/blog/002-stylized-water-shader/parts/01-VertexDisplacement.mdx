## Chapter I: Vertex displacement

My first attempt began with the most straightforward idea: if you want waves, move the surface up and down.

That's the essence of vertex displacement. Each vertex runs through a function of sine waves or noise, time is
added in, and the mesh begins to ripple. Intuitively, the more vertices you have, the smoother the motion looks, less
guessing between points.

It worked, but it still wasn't enough. Even with vertices shifting around, the surface looked strangely flat.

The reason? ==Normals==.

<br />

### What is a normal?

I had to remind myself what they are and how they work, normals are just 3D unit vectors that tells the renderer which
way a surface is facing. Without them, light has no idea how to bounce, and everything looks dull and flat.

They're stored per vertex and interpolated across triangles (primitives), so each ==fragment== gets an orientation.
That works fine for static meshes, but when you start moving vertices around, the normals need to move too, otherwise
the lighting no longer matches the shape.

<blockquote>
Worth mentioning that a vertex can be associated with only one normal. This is problematic when we have sharp edges, 
like in a cube for example. Duplicating vertices allows each copy can carry its own normal.

Normals define how light hits a surface, but there was still a missing piece for me: what exactly are those normals
shading? The answer lies in ==fragments==.

I owe that clarity to Mike, an interviewer I once spoke with. I already had a rough idea of what a fragment was,
but he explained it in such a clear and patient way that it finally stuck.

<br />

### What is a fragment?

Internally, all meshes are broken down into tiny triangles (primitives). When one of those triangles overlaps a pixel
on screen, the rasterizer produces a fragment: a candidate contribution to that pixel's final color.

Each fragment runs through the _fragment shader_ (called a _pixel shader_ in DirectX), gets a color, and then competes
in depth and blending tests. Some survive, some are discarded, meaning work was done only to be thrown away.

<blockquote>
Shading fragments that never affect the final image is called **overdraw**. GPUs reduce it with early depth tests or
front-to-back rendering, but with transparency or other blending modes, even hidden fragments may still contribute.

### Shading waves

On my first water mesh, all normals pointed straight upward. Light bounced uniformly, and the ripples looked lifeless.

To fix that, I had to recompute normals dynamically. A common trick is the ==neighbor technique==:

1. Pick two nearby points, slightly offset on X and Z by a small `ε`.
2. Raise them using the same displacement function.
3. Build two direction vectors from the current position to those neighbors.
4. Cross them, normalize, and you get a new normal pointing outward from the displaced surface.

<br />

```typescript
class WaterMaterial extends MeshBasicNodeMaterial {
  // ...
  private computeElevation = Fn(([posXZ = vec2(0)]) => {
    /* ... */
  });

  private computeNormal = Fn(() => {
    const epsilon = float(0.01); // tune to your world scale

    const xNeighbor = positionLocal.add(vec3(epsilon, 0, 0));
    const zNeighbor = positionLocal.add(vec3(0, 0, epsilon));

    const elevX = this.computeElevation(xNeighbor.xz);
    const elevZ = this.computeElevation(zNeighbor.xz);
    const elev = this.computeElevation(positionLocal.xz);

    const posX = xNeighbor.add(vec3(0, elevX, 0));
    const posZ = zNeighbor.add(vec3(0, elevZ, 0));
    const pos = positionLocal.add(vec3(0, elev, 0));

    const toX = normalize(posX.sub(pos));
    const toZ = normalize(posZ.sub(pos));

    return normalize(cross(toX, toZ));
  });
  // ...
}
```

The catch was picking the offset `ε`. Too small and I'd get floating-point noise, too large and I'd smear away detail.
And since each neighbor adds another texture fetch, the cost went up fast with vertex count.

When I got it right, the ripples finally caught light. They weren't perfect, but they had life.

> In my own version, I used a slight variation: instead of elevating three points, I approximated slopes, built
> tangent and bitangent vectors, and crossed those. Mathematically it's equivalent. At the time it felt cleaner since
> I only dealt with elevations, but looking back, the three-points method is easier to picture. If I were starting fresh
> today, I'd probably choose that.

<br />

### Outcome

While experimenting, I stumbled across a great [demo by Dan Greenheck](https://www.youtube.com/watch?v=jK4uXGY07vA).
His WebGL version of the neighbor trick looked fantastic.

My take was simpler: I leaned on a precomputed noise texture (Perlin, Voronoi, Turbulence packed into RGB) instead of
multi-octave procedural noise. It was cheaper, good enough, and kept things moving.

The real limit wasn't sampling, though, it was geometry. Displacement can only move vertices that exist. A coarse
mesh means blocky ripples, no matter how good the math. To solve that, I built a custom lake mesh in Blender:
enough subdivisions where water was visible, none wasted under terrain.
