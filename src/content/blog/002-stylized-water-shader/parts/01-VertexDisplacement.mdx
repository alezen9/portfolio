## Chapter I: Vertex displacement

My first attempt began with the most straightforward idea: if you want waves, move the surface up and down.

That's the essence of vertex displacement. Conceptually easy to grasp, practically...easy with reservations.

Starting with a flat mesh, each vertex runs through a function of sine waves or noise, make `time`
part of the input and the mesh begins to ripple. Intuitively, the more vertices you have, the smoother the motion
looks, less guessing between points.

This is the easy part. It works, but it is not enough. Even with vertices shifting around, the surface looked strangely
flat.

The culprit? ==Normals==.

<br />

### What is a normal?

I had to remind myself what they are and how they work: essentially, normals are just 3D unit vectors that tell the
renderer which way a surface is facing. Without them, light has no idea how to bounce, and everything looks dull and
flat.

They're stored per vertex and interpolated across triangles (primitive), so each ==fragment== gets an orientation.

Geometries usually bring plenty of precomputed data, normals are one of them. That works fine for static meshes, but
when I started moving vertices around, the normals didn't magically auto-update, hence the flat look.

This is the "with reservations" part: I had to compute and update the normals according to my displacement, for the lighting to
match the new shape.

<blockquote>
Not my case, but worth mentioning for the curious: a vertex can be associated with **only one** normal. This is problematic when we have sharp edges, 
like in a cube for example. Duplicating vertices allows each copy to carry its own normal.

So, normals define how light hits a surface, but what exactly are they shading? The answer is ==fragments==.

I already had a rough idea of what a fragment was, but I owe the clarity I have now to Mike, an interviewer I once
spoke with. He explained it in such a clear and patient way that it stuck.

Allow me to echo his explanation here.

<br />

### What is a fragment?

Combine a geometry (the skeleton) with one or more materials (the skin), and you get what's called a mesh.

Internally, all geometries are broken down into tiny triangles. When one of those triangles overlaps a pixel on screen,
the rasterizer produces a fragment: a **candidate** contribution to that pixel's final color.

As you can imagine, multiple elements in the scene may overlap:

<br />

<br />

Here, the same pixel is covered first by the sky, then the ground, then a box, and finally a sphere. Each
overlap generates a fragment, but only the front-most opaque one wins.

In a usual 3D pipeline: each mesh runs through a series of steps, executing a program (shader) each with a specific
responsibility. Two of the most known are the _vertex_ and the _fragment_ shaders (called a _pixel shader_ in DirectX).

So, each fragment runs through the fragment shader, gets shaded, and then competes in depth and blending tests with
other fragments that target the same pixel. Some survive, some are discarded, meaning work was done only to be thrown
away.

> Shading fragments that never affect the final image is called **overdraw**. GPUs mitigate it with early depth tests
> or front-to-back rendering, but with transparency or other blending modes, even hidden fragments may still contribute.

<br />

### Shading waves

Since I started with a flat mesh, all precomputed normals pointed straight upward. Light bounced uniformly, and the
ripples looked lifeless.

To fix it, I had to recompute normals dynamically. A common trick is the ==neighbor technique==:

1. Pick two nearby points, slightly offset on X and Z by a small `ε`.
2. Raise them using the same displacement function.
3. Build two direction vectors from the current position to those neighbors.
4. Cross them, normalize, and you get a new normal pointing outward from the displaced surface.

<br />

```typescript
class WaterMaterial extends MeshBasicNodeMaterial {
  // ...
  private computeElevation = Fn(([posXZ = vec2(0)]) => {
    /* ... */
  });

  private computeNormal = Fn(() => {
    const epsilon = float(0.01); // tune to your world's scale

    const xNeighbor = positionLocal.add(vec3(epsilon, 0, 0));
    const zNeighbor = positionLocal.add(vec3(0, 0, epsilon));

    const elevX = this.computeElevation(xNeighbor.xz);
    const elevZ = this.computeElevation(zNeighbor.xz);
    const elev = this.computeElevation(positionLocal.xz);

    const posX = xNeighbor.add(vec3(0, elevX, 0));
    const posZ = zNeighbor.add(vec3(0, elevZ, 0));
    const pos = positionLocal.add(vec3(0, elev, 0));

    const toX = normalize(posX.sub(pos));
    const toZ = normalize(posZ.sub(pos));

    return normalize(cross(toX, toZ));
  });
  // ...
}
```

Be mindful when picking the offset `ε`: too small and you might get floating-point noise, too large and detail can smear
away. Also, since each neighbor adds another texture fetch, the cost goes up fast with vertex count.

When I got it right, the ripples finally caught light. They weren't perfect, but the surface wasn't flat anymore.

> In my own version, I used a slight variation: instead of elevating three points, I approximated slopes, built
> tangent and bitangent vectors, and crossed those. Mathematically it's equivalent. At the time it felt cleaner since
> I only dealt with elevations, but looking back, the three-points method is easier to picture. If I were starting fresh
> today, I'd probably choose that.

### Outcome

While researching, I stumbled across this great [demo by Dan Greenheck](https://www.youtube.com/watch?v=jK4uXGY07vA).
His WebGL version of the neighbor trick looked fantastic.

My take was simpler: I leaned on a precomputed noise texture (Perlin, Voronoi, Turbulence packed into RGB) instead of
multi-octave procedural noise. It was cheaper at the cost of richness, but good enough.

The real limit wasn't sampling, though, it was geometry. Displacement can only move vertices that exist. A coarse
mesh means blocky ripples, no matter how good the math. To mitigate that, I built a custom lake mesh in Blender:
enough subdivisions where water was visible, almost none wasted under terrain.
