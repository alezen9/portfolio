## 5. Compositing

By now, the browser has rasterized tiles for everything that needs to be drawn. But it still needs to figure out how to stack them together into the final frame.  
This step is called compositing.

<br />

### Layers: not all elements are equal

Most elements just get painted into their parent's layer.  
But some elements are "promoted” to their own compositing layer.

Think of Photoshop: instead of merging everything onto one canvas, some pieces stay separate so they can be moved and blended independently.

Browsers use heuristics to decide which elements deserve their own layer:

- `transform` (e.g. `translate`, `scale`, `rotate`)
- `opacity`
- `will-change`
- `position: fixed` or `sticky`
- `filter`, `mask`, `clip-path`
- `<video>`, `<canvas>`

<br />

Not every case is promoted: a small transformed icon might stay in its parent layer, while a large moving panel gets a GPU-backed layer.

**In my scenario**: Safari didn't promote the moving circular mask by default (its heuristics didn't consider it worth a layer),
so every frame triggered a repaint. Adding `transform: translateZ(0);` forced Safari to create a dedicated GPU layer.  
Once promoted, Safari could just move the layer's bitmap instead of repainting the mask every frame &rarr; smooth.

<br />

### Main thread vs compositor thread

- **Main thread** handles: Style &rarr; Layout &rarr; Paint.
- **Compositor thread** (separate, usually one per tab) assembles rasterized layers into frames.

If only compositor-friendly properties change (`transform`, `opacity`, `filter`),  
the compositor thread can animate them smoothly at the display's refresh rate (e.g. 60Hz, 120Hz, or higher) without waiting on the main thread.

If a change affects Layout or Paint (`width`, `top`, `color`), the main thread is pulled back in, slowing things down.

### GPU transforms

Once an element is on its own layer, **transform and opacity changes are applied on the GPU**.  
Internally, this is done by shaders applying matrix multiplications to the layer's texture in screen space (no need to re-draw the content).

**Cheap, smooth, hardware-accelerated.**

This is why `transform: translateX(...)` is safe to animate, while `left: ...` isn't.  
`left` forces: Layout &rarr; Paint &rarr; Composite.

### Why compositing isn't always free

- **More layers = more GPU memory**  
  Overusing `will-change` or `translateZ(0)` can blow up GPU memory.

- **CPU &rarr; GPU upload cost**  
   Every new or updated layer must be uploaded from system memory to GPU memory (VRAM).  
   This is a universal bottleneck in graphics pipelines, not just browsers.

  > **Note:** This transfer crosses the CPU↔GPU bus (PCIe on desktop, shared bus on mobile), which is orders of magnitude slower than the GPU's own internal bandwidth.  
  >  In other words: GPUs are insanely fast once data is in VRAM, but _getting it there_ is slow.  
  >  That's why minimizing repaints and unnecessary layer promotions matters for performance.

  > **Fun fact:** In game development, this is often referred to as the _PCIe tax_.

  > **Note:** In Chrome DevTools, Performance panel, you can see upload cost show up as **Commit** events, where the browser flushes updated tiles/textures to the GPU.

- **Blending cost**  
  Multiple overlapping translucent layers mean more GPU work per pixel.

- **Text quirks.**  
  Promoted layers may disable subpixel antialiasing &rarr; text can look blurrier.

So Compositing is powerful, but you want to use it surgically, not everywhere.

<br />

### Output of this stage

The compositor thread now has a set of layers and instructions on how to stack and move them.  
These layers are handed to the GPU, which blends them into the final frame.
