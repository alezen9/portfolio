## Why Bother with the Rendering Pipeline?

The thing about frontend performance problems: sometimes they look random, and every browser seems to behave a little differently.  
But under the hood, every browser follows the same broad sequence of steps to turn HTML and CSS into pixels on the screen, even if the exact implementation details differ.
This sequence is called the ==Rendering Pipeline==.

<br />

Knowing how that pipeline works doesn't just satisfy curiosity, it changes the way you debug and build:

- **You stop guessing.**  
  Instead of _"maybe reducing the mask size will help"_, you can check: _"Is the bottleneck ==Style==, ==Layout==, ==Paint==, or ==Compositing=="_?

- **You know which properties are safe to animate.**  
  `transform` and `opacity` are compositor-friendly, while `top`, `left`, or `width` force Layout and Paint.

- **You see why browser differences happen.**  
  Chrome and Safari use different heuristics for promoting elements to GPU layers, which explains why my fix was needed in one and not the other.

- **You make better design calls early.**  
  You'll know when a heavy blur, mask, or filter will eat GPU cycles, and when it's safe to use them.

<br />

In other words: understanding the rendering pipeline gives frontend developers a kind of x-ray vision.

You don't need to memorize every detail, but even a rough mental model helps you reason about performance issues instead of relying on Stack Overflow magic.

## The Rendering Pipeline in a Nutshell

Before diving deep into each stage, it helps to have a high-level map of what actually happens when a browser renders a page.

At a conceptual level, every browser engine follows the same six broad stages to turn code into pixels:

1. **Parsing**
   - HTML is parsed into the DOM (Document Object Model).
   - CSS is parsed into the CSSOM (CSS Object Model).

2. **Style Recalculation**
   - The DOM and CSSOM are matched together (the engine resolves which CSS rules apply to which DOM nodes).
   - Each element gets its computed styles — the final property values after cascade, inheritance, and variables are resolved.

3. **Layout (Reflow)**
   - The browser uses computed styles to calculate geometry: positions, sizes, line breaks.
   - Produces a layout tree (sometimes called the _frame tree_ or _render tree_), which maps where every visible element goes.

4. **Paint & Rasterization**
   - Paint: elements are turned into drawing commands (a display list).
   - Rasterization: those commands are converted into pixels, usually in tiles (bitmaps).

5. **Compositing**
   - Some elements are promoted into independent layers (often GPU-backed).
   - The compositor thread assembles these layers into the final frame.

6. **Display**
   - Finally, the GPU swaps the backbuffer with the frontbuffer during VSync, and the pixels appear on screen.

<br />

### Engine differences

While the high-level pipeline is the same across browsers, each engine has its own quirks in how it structures these stages:

- **Blink (Chrome/Edge):**  
  Splits the Paint stage into extra phases: ==Pre-Paint== which figures out what needs repainting, and ==Layerize== which decides which elements become GPU-backed layers.

- **WebKit (Safari):**  
  Sticks closer to the canonical six stages. Invalidation logic is folded into _Paint_, and layer promotion is handled by its ==RenderLayer== system.

- **Gecko (Firefox):**  
  Uses **WebRender**, which parallelizes style calculation in Rust (via Servo's Stylo engine) and hands the display list directly to the GPU. Rasterization and compositing are mostly GPU-driven.

<br />

Conceptually, though, they're all doing the same job:<br />
**==Parse &rarr; Style &rarr; Layout &rarr; Paint &rarr; Composite &rarr; Display==**
