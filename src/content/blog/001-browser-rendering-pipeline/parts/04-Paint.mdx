## Paint & Rasterization

At this point, the browser knows what every element looks like (computed styles) and where everything goes (layout tree).  
The next step is to actually draw pixels.

<br />

### What happens here

The browser walks the layout tree and generates a ==display list==, a sequence of draw commands like:

```
FillRect(x=0, y=0, w=200, h=100, color=red)
DrawText("Hello", font=Arial, size=16, x=108, y=70)
```

These commands are not pixels yet. Think of them as vector instructions.
Rasterization samples those vector-like commands onto the pixel grid, per tile, producing the bitmap for each tile.

> **Note:** _Rasterization_ is one of several ways to transform geometry into images.  
> 3D engines might use _ray tracing_ or _path tracing_, but browsers stick to rasterization because it's fast and highly parallelizable.

<br />

### Where it runs (CPU vs GPU)

The **CPU** typically constructs the display list.  
Rasterization can happen on either CPU or GPU, depending on engine and hardware.

<br />

**Engine differences**

- Chrome's Blink, for example, uses ==Skia== as the graphics library to rasterize tiles, GPU-accelerated by default.
- Safari's WebKit relies on ==Core Graphics== / ==Core Animation==.
- Firefox's Gecko uses ==WebRender==, which sends the display list directly to the GPU, making rasterization and compositing fully GPU-driven.

<br />

### Tiling

Instead of painting the whole page at once, the browser splits it into tiles (e.g. 256&times;256 px or 512&times;512 px).

Each tile is rasterized independently, often in parallel across threads or GPU cores.

**Why tiles?**  
If only a small part of the screen changes, only those tiles need to be re-rasterized.

> **Note:** You can visualize this in Chrome DevTools by pressing **Cmd+Shift+P** / **Ctrl+Shift+P** to open the Command Menu &rarr; type _"Show Rendering"_ and select it.  
> In the Rendering drawer enable Paint flashing (repainted regions flash green).
> You can also toggle Layers borders to outline compositor layers or check GPU memory usage and fps by enabling Frame Rendering Stats.

<br />

### Why Paint can be expensive

Paint cost scales with how many pixels you touch and how complex each pixel is to compute.  
Not all properties are equal.

For example:

- Cheap: `background-color`, `border`, simple fills.
- Expensive: large `box-shadow`s, gradients, `mask-image`, CSS filters, backdrop filters.
- Large area repaints (e.g. animating `background-color` on `<body>`) are especially costly.

Animating Paint-heavy properties means new tiles must be rasterized every frame, which can quickly cause jank.

<br />

### Output of this stage

A set of rasterized tiles (pixel buffers/bitmaps). If rasterized on the CPU, these bitmaps are uploaded as GPU textures. If rasterized on the GPU, they're already textures.
The compositor then samples and blends them to assemble the frame.
