## 13. GPU culling: aiming higher

I first heard about this approach through [Acerola's grass videos](https://www.youtube.com/@Acerola_t). I have watched them more
times than I can remember. I like the way he explains things, I like his humour, and I consider him highly competent. When he said
that stream compaction was complicated, I believed him.

I still wanted to understand it.

From there I went through YouTube videos, GPU Gems and several websites I unfortunately cannot trace back anymore. The algorithm
that eventually started to click was the Blelloch scan, helped mostly by a video that was only four minutes long.

It took me considerably longer than that, with plenty of pausing, rewinding and eventually a piece of paper because apparently the
screen was no longer enough. I still have that paper. It is covered in faint numbers, crossed-out indices and arrows which barely
make sense to me now, so a clean text example will probably do a better job here.

Before looking at the algorithm itself, there are three terms worth separating because I often found them used very close to one another:

- **stream compaction** &rarr; the goal: take a sparse set of survivors and pack them into a continuous output
- **prefix sum**, or **scan** &rarr; the operation that calculates where each survivor should go
- **Blelloch scan** &rarr; one parallel algorithm for calculating that prefix sum

<br />

### What the prefix sum gives us

Start with eight blades and one visibility flag for each of them:

```text
items:  A  B  C  D  E  F  G  H
keep:   1  0  1  1  0  0  1  1
```

On a CPU, I could walk from left to right with a counter and append every item whose flag is `1`:

```text
output: A  C  D  G  H
```

If I write down the value of that counter before visiting each item, I get this:

```text
scan:   0  1  1  2  3  3  3  4
```

This is an **exclusive prefix sum**. Exclusive means that an element does not include its own flag in the sum. Each value simply answers the question: how many surviving items came before me?

That answer also happens to be the destination of every survivor:

```text
A: keep 1, scan 0  -> output[0]
C: keep 1, scan 1  -> output[1]
D: keep 1, scan 2  -> output[2]
G: keep 1, scan 3  -> output[3]
H: keep 1, scan 4  -> output[4]
```

The discarded blades have scan values too, but they simply do not write anything. Every surviving blade receives a unique output position, and none of them had to increment a shared counter to get it.

That result is exactly what I wanted. Producing the scan row in parallel is where it gets more complicated. Every value appears to
depend on everything to its left, which sounds very much like the kind of sequential loop we are trying to avoid.

<br />

### Going up

Blelloch scan solves this in two phases. The first one is the **up-sweep**, sometimes called the reduce phase. Instead of walking through the entire array, it combines neighboring groups into progressively larger partial sums.

We start with the visibility flags:

```text
[1, 0, 1, 1, 0, 0, 1, 1]
```

At the first level, split the values into pairs and add the left value of every pair into the right one:

```text
[1, 1, 1, 2, 0, 0, 1, 2]
```

The values at indices `1`, `3`, `5` and `7` now contain the totals for groups of two:

```text
[1+0, 1+1, 0+0, 1+1]
   1      2      0      2
```

At the second level, combine those pairs into groups of four. The total of the left half is added into the total of the right half:

```text
[1, 1, 1, 3, 0, 0, 1, 2]
```

Index `3` now contains the total of the first four flags, while index `7` contains the total of the last four. One final addition combines the two halves:

```text
[1, 1, 1, 3, 0, 0, 1, 5]
```

The last cell now contains `5`, which is the total number of surviving blades.

There is no actual tree stored somewhere in memory. The tree is just a useful way to picture which groups interact at every level. All the additions on one level are independent and can happen in parallel, but each level has to finish before the next one begins.

For eight values, the total reaches the top after three ordered levels. Adding more values still adds work, of course, but it does not add one ordered step per value. The depth grows logarithmically.

At this point we have the total, but not the scan row. The partial sums now need to travel back down through the same structure.

Before that starts, save the total and replace the last cell with `0`:

```text
total: 5
array: [1, 1, 1, 3, 0, 0, 1, 0]
```

That zero represents the prefix entering the complete array. Nothing comes before the first element, which is also what eventually makes the result exclusive.

<br />

### Coming back down

The **down-sweep** applies the same small operation to every pair, starting from the widest one and working back towards the original neighbors:

1. Save the old value on the left.
2. Move the prefix from the right into the left.
3. Add the saved left value to that prefix and store the result on the right.

At the widest pair, the old left value is `3` and the prefix on the right is `0`:

```text
before: left = 3, right = 0
after:  left = 0, right = 3

[1, 1, 1, 0, 0, 0, 1, 3]
```

The left half has nothing before it, so its prefix is `0`. The right half has the three survivors from the left half before it, so its prefix is `3`.

Apply the same rule to the two groups below it:

```text
[1, 0, 1, 1, 0, 3, 1, 3]
```

Then apply it once more to the original neighboring pairs:

```text
[0, 1, 1, 2, 3, 3, 3, 4]
```

That is the exclusive scan we were looking for:

```text
items:  A  B  C  D  E  F  G  H
keep:   1  0  1  1  0  0  1  1
scan:   0  1  1  2  3  3  3  4
```

It is worth reading it normally again after all those steps. Before `A` there are `0` survivors. Before `B` there is `1`. Before `D` there are `2`, and before `H` there are `4`. The up-sweep collected the partial sums, planting the zero established the first prefix, and the down-sweep distributed the correct prefix to every position.

Blelloch scan performs linear total work across all its levels, but the ordered depth is logarithmic. The number of additions still grows with the number of elements. The useful part is that many of those additions can happen at the same time.

<br />

### Compacting the stream

Once the scan exists, the actual compaction is fairly straightforward. Every thread already knows its original blade index, whether the blade survived and the output position stored in the scan.

Only the surviving threads write:

```text
input A writes itself to output[0]
input C writes itself to output[1]
input D writes itself to output[2]
input G writes itself to output[3]
input H writes itself to output[4]
```

The final visible list becomes:

```text
[A, C, D, G, H]
```

The total saved at the end of the up-sweep, `5`, becomes the instance count in the indirect buffer. Conceptually, this produces the same two things as my atomic implementation: a compact list of visible blade indices and the exact number of entries the renderer should draw.

The prefix sum is therefore not doing the culling itself. It turns the visibility flags produced by the culling pass into collision-free output addresses.

<br />

### Eight values were the friendly version

My piece of paper had eight values. The grass field is a 1024 &times; 1024 grid: exactly 1,048,576 blades.

Both counts are powers of two, which is convenient because every level splits cleanly in half. A less cooperative count would
usually need padding to the next block-sized boundary or special handling for its final partial block.

A small scan fits inside one GPU workgroup, where its threads can share fast local memory and synchronize between every level of the up-sweep and down-sweep. 1M values need many workgroups, and separate workgroups cannot stop halfway through one dispatch and synchronize with each other.

The large version therefore becomes a hierarchy of smaller scans:

1. Scan every workgroup-sized block independently.
2. Save the total produced by each block.
3. Scan the smaller array containing those block totals. If that array is still too large, repeat the same idea again.
4. Add the resulting block offsets back to the values inside each block.
5. Scatter the surviving blade indices into the final compacted list.
6. Write the total survivor count into the indirect draw arguments.

These are conceptual stages rather than a promise that every implementation uses exactly six dispatches. The precise pipeline depends on the workgroup size, the scan implementation and the way its intermediate buffers are arranged.

That list describes the proper hierarchical version. My first implementation took a more direct route instead.

I first tried putting all the up-sweep and down-sweep levels inside GPU loops. It looked like the neat option and appeared faster
than driving the levels from JavaScript, but every level depends on the previous one being complete. A workgroup barrier can only
synchronize threads inside one workgroup, not the whole 1M-entry dispatch, so I could not trust the result once the scan crossed
those boundaries.

I tried the blunt version too: JavaScript issued one compute dispatch for every level and waited before starting the next one.
Since 1,048,576 is 2<sup>20</sup>, that meant `20` ordered passes going up and another `20` coming back down, plus the identity reset
and final compaction. The ordering was no longer ambiguous, but the incomplete pipeline was already making performance worse.

Moving from that experiment to the proper hierarchy above meant adding the local scans, intermediate block totals, another scan
over those totals, offsets to propagate back and the final scatter. I also had to express all of it through TSL, while the
documentation left several of my questions unanswered. I ended up digging through the Three.js source just to understand how the
indirect storage buffer was supposed to reach the geometry.

Some attempts produced incorrect indices. Others made performance worse instead of better. By then a bad value could have come
from almost any level of the scan, the compaction or the indirect draw, with very little visibility between them. Continuing to
change things felt more like guessing than debugging, so I stopped.

I am not blaming prefix-sum compaction for any of this. It can absolutely work for grass. My implementation had simply accumulated
too many unverified boundaries for the time I could justify spending on it, so I left it there with the intention of returning one
day.

For now, atomic add is what I shipped. It keeps the whole visibility-to-draw path on the GPU and got the lake area back to 120 FPS
on my laptop. That was enough for me to stop treating it like a consolation prize.

I still wanted to explain the failed version properly because the main idea is genuinely elegant once it clicks. If this small example saves someone else a few rounds of staring at the same eight numbers, then at least my piece of paper served a purpose after all.
