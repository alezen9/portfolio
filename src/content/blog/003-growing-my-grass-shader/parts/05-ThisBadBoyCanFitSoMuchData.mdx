## 5. This bad boy can fit so much data

With the bigger pieces finally falling into place, I allowed myself a small side quest.

Nothing was broken. Performance was already in a good place. This wasn't about fixing a bottleneck or chasing extra FPS.
I was simply curious.

I had heard about bit packing before, but I had never actually gone down that rabbit hole. It always felt like one of
those techniques you know exists, but never quite touch unless you really need it. This felt like a good opportunity to
finally explore it properly.

At that point, each grass blade was already carrying a fair amount of state: offsets, scale, wind parameters, visibility
flags, noise factors. In earlier iterations I had a few `vec4` buffers, three if I recall corretly, with slightly less state
overall. In the current version, everything fits into one `vec4` plus a single extra `float`, which I later added for vertical
displacement, and has still plenty of room left to store more data.

Memory usage is obviously lower this way, even if it wasn't a real problem to begin with. That alone didn't justify the
effort. What interested me more was understanding how and when this kind of packing makes sense.

Conceptually, bit packing is about accepting that not all data deserves the same precision.

A grass blade doesn't need a full 32-bit float to say whether it's visible. It doesn't need perfect precision to store a wind phase, a
scale factor, or a small rotation. Most of these values live in tight ranges, or are simple on/off flags.

So instead of giving each one its own float, I started treating a single value as a tiny container.

I take a number with a known range, map it into a fixed number of discrete steps, and store it in a specific slice of bits. Later,
I reverse the process and reconstruct an approximation of the original value.

Here's what that looks like at a very concrete level:

```
initial value (all bits zero)
00000000 00000000 00000000 00000000

after storing visibility = 1 in bit 0
00000000 00000000 00000000 00000001

after storing yaw angle in bits 1-8
00000000 00000000 00000010 10000001
                         ↑ ↑↑↑↑↑↑↑
                         quantized angle (8 bits)
```

During the process, a number like `0.50334532` might come back as `0.503`. That loss of precision is real, but for grass, after a bit of tuning it's
visually meaningless. Some values needed more care than others: positions and height offsets required finer granularity, while
things like yaw rotation could be heavily quantized without anyone noticing, since they're already randomized by design.

> Although we talk about a "32-bit value", this is still a floating-point number. In practice, that means I'm not using all 32 bits
> freely. A float gives you about 24 bits of reliable integer precision (the mantissa), and I deliberately stay within that budget.
>
> That's not a limitation I ran into, it's one I chose.
>
> By keeping the total number of packed bits under that ~24-bit threshold, I avoid precision loss and bit corruption entirely. Flags
> stay stable, angles decode consistently, and everything round-trips safely. The remaining loss of precision comes only from
> intentional quantization, not from floating-point artifacts.

I won't go deep into the helpers here, but if you're curious, all the packing and unpacking utilities live in
[this](https://github.com/alezen9/revo-realms/blob/feat/new-world/src/utils/TSLUtils.ts) dedicated file that I reuse across systems.

After implementing this, I didn't suddenly gain a bunch of extra performance. That was never the goal, and I don't have
measurements claiming otherwise. The most obvious win is the reduction in memory footprint, which is nice but not
game-changing on its own.

What really mattered to me was everything else. Grass may not have needed bit packing, but I now understand it because I've actually
used it. The knowledge I gained is far more valuable to me than a few saved bytes in this specific system.

It turned a vague concept into something concrete, and that experience is now part of my toolbox. If I ever run into a
system where memory layout or bandwidth really does matter, I won't be starting from zero.

That's ultimately why this section exists at all: not because bit packing saved the day here, but because it was a
worthwhile detour, and one I'm glad I took.
